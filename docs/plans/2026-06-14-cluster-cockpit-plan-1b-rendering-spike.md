# Cluster Drill Cockpit — Plan 1b: Matrix Rendering Spike — Plan

> **For agentic workers:** This is a **spike**, not a TDD build plan. Its deliverable
> is a *decision* + a captured, working dashboard JSON that becomes the contract for the
> follow-on build plan (`1b-build`). Steps are exploratory; run them against the live
> Grafana, capture evidence, decide. Do NOT write `render_cluster_dashboard` here — that
> is the build plan, written once this spike picks the mechanism.

**Goal:** Decide *how* to render the node × component cluster matrix (colored cells,
grouped headers, inline DRBD replication band, cluster-unit summary, first-class
integrity alarm) in the lab's actual Grafana, by prototyping it against the **live
`cluster_*` metrics** the Plan 1a collector now emits — and capture the winning
dashboard JSON as the build contract.

**Architecture:** Build the matrix two-to-three ways as hand-authored dashboard JSON,
load each into the running Grafana (`obs` box, `:3000`) via the provisioning dir,
evaluate against fixed criteria, pick one, and freeze the winning panel JSON + the
metric→matrix transformation recipe into the design spec.

**Tech Stack:** Grafana (provisioned dashboards under `/var/lib/grafana/dashboards`),
Prometheus (`job="node"`, the `cluster_*` series), the Plan 1a collector, `ansible`
ad-hoc from the host venv (post-`uv sync`).

**Spec:** `docs/specs/2026-06-14-cluster-drill-cockpit-design.md` §5 (rendering —
spike-decided), §3.1 (matrix + integrity alarm), §4.3 (fail-loud/STALE precedence).

**Prerequisite:** Plan 1a landed (collector emits `cluster_*` — verified live, commit
`3595d35`). The lab must be **up** with the collector deployed (timer running, or run
the collector once into the textfile dir) so real series exist to render.

## Background the spike-runner needs

- The existing dashboard is generated by `src/mqlab/dashboard.py:render_dashboard(topo)`
  and deployed by the `grafana` role from `build/grafana/dashboards/lab-status.json`
  to `/var/lib/grafana/dashboards/` (provider config: `dashboards.yml.j2`). The cockpit
  is a **separate** dashboard (new `uid` `lab-pcmk-cluster`), deployed as a *second*
  file alongside `lab-status.json` — not a change to `lab-fleet-node`.
- The matrix cell's natural Grafana analog already exists in that file:
  `_net_health_panel` — a `stat` panel with `value`→`{text,color}` mappings
  (grey/red/orange/green). A matrix is, at heart, a grid of these.
- The live metrics to render (confirmed in Plan 1a Task 10), labelled `node` =
  reporting node, on `job="node"`:
  - `cluster_quorate`, `cluster_node_online{member}`, `cluster_node_unclean{member}`
  - `cluster_resource_started{resource}`, `cluster_resource_owner{resource,holder}`
  - `cluster_drbd_role{resource,role}`, `cluster_drbd_disk{...,disk}`,
    `cluster_drbd_conn{...,conn}`, `cluster_drbd_resync_pct`,
    `cluster_drbd_out_of_sync_bytes`
  - `cluster_iscsi_sessions`, `cluster_daemon_up{unit}`
  - `cluster_fence_count{member}`
  - `cluster_state_last_write_timestamp{source}` (the STALE clock)
- **The crux:** these are *separate series with different label sets*. A node×component
  matrix needs them aligned into one node-keyed table (rows = nodes, columns =
  components). The spike's central question is whether Grafana's table transformations
  (Merge / Labels-to-fields / Join-by-field) can assemble that cleanly, vs. a
  per-cell stat grid, vs. a Canvas.

## Evaluation criteria (decide against these)

Score each prototype 1–5:

1. **Reads as the mockup** — node rows, component columns grouped by layer
   (membership/storage/resource/fence), colored cells, ★ owner, the cluster-unit
   summary, the inline DRBD replication band. (Fidelity.)
2. **Mid-drill legibility** — when a value flips (resource relocates, DRBD →
   StandAlone, node fenced), does the change read at a glance?
3. **Fail-loud / STALE** — can a missing/old series render visibly STALE (distinct from
   green and red), driven by `cluster_state_last_write_timestamp`?
4. **Integrity alarm** — can split-brain (`cluster_drbd_conn{conn="StandAlone"}` /
   dual-Primary) trip a *loud, distinct* top-of-board signal, not just a cell?
5. **Code-generatable** — can `render_dashboard`-style pure-Python emit this JSON
   maintainably (DRY across nodes/columns), and survive a Grafana restart via
   provisioning?
6. **Effort to build + maintain** — author cost and JSON verbosity.

### Task 3: Prototype A — colored-cell Table

- [ ] Author `build/grafana/dashboards/spike-matrix-table.json`: a single dashboard
  with one `table` panel that assembles node-keyed rows. Approach: one Prometheus
  target per component metric (`instant`, `format: table`), then transformations:
  - `Merge` to combine the per-metric tables;
  - `Labels to fields` (keep `node` as the row key);
  - per-column **field overrides** → cell display mode `color-background` with value
    mappings (the `_net_health_panel` color vocabulary).
- [ ] Push it via provisioning and reload:

```bash
$WT/.venv/bin/ansible obs_box -i $INV -b -m copy \
  -a "src=$WT/build/grafana/dashboards/spike-matrix-table.json dest=/var/lib/grafana/dashboards/spike-matrix-table.json mode=0644"
# provider auto-loads from that dir within its poll interval (~10s)
```

- [ ] Open Grafana in a browser (the lab's `:3000`), screenshot, score against the
  criteria. Note specifically: can grouped headers be faked by column naming? Do the
  enum metrics (`cluster_drbd_conn{conn=...}`) collapse to one cell cleanly? Does the
  Merge align rows by `node` without duplicate-column blowups?

### Task 4: Prototype B — per-cell Stat grid

## Exit criteria

The spike is done when: (1) a mechanism is chosen with a filled scorecard; (2) a
working dashboard JSON for the matrix exists against live metrics and is captured under
`docs/specs/diagrams/`; (3) the integrity alarm and STALE treatments are demonstrated;
(4) the design spec §5 carries the decision record + the exact recipe the build plan
will encode. Then write **Plan 1b-build** (`render_cluster_dashboard` TDD + grafana-role
second-dashboard deploy) from that frozen contract.
