# OpenTelemetry for the lab: docs-only R&D (#1507)

**Date:** 2026-10-14
**Issue:** `mq-resiliency-lab-for-linux#1507` (ad hoc).
**Status:** R&D complete. **Decision deferred.** No spikes were run and no follow-up
issues were filed. This report is the whole output.
**Scope:** what OpenTelemetry (OTel) would add on top of the lab's current
observability; what IBM MQ 10.0 and our existing stack already support; what extra
infrastructure adoption would need; and whether the lab could demonstrate IBM's newer
OTel features. All of it comes from documentation, upstream source code, and reading
this repo. No lab guest was touched, because the cloud lab was busy with validation
work.

> Convention: each claim is tagged **[data]** (what a cited source actually says) or
> **[judgment]** (our reasoning on top). IBM Docs pages were fetched with
> `tools/ibm_doc_cache.py` and cached under
> `build/cache/refs/ibm-docs/<product>/<version>/<slug>/content.txt`. The URLs below are
> those pages' `source_url`.

## 1. Bottom line

- **[data]** On distributed MQ (Linux, Windows, AIX), the **queue manager emits trace
  spans only through an optional, separately downloaded API exit**: the Instana "IBM MQ
  Tracing" exit, which IBM calls a "supporting program" [S1][S2][S3]. Built-in,
  queue-manager-side OTel tracing exists only on **z/OS** (MQ 10.0) [S5] and the
  **MQ Appliance** (its own tracing service, 9.4.3) [S10]. Nothing in the docs shows it
  was ever bundled on distributed platforms: 9.3.5 also shipped it as a separate
  supporting program [S3].
- **[data]** Client-side **propagation** of trace context *is* built in: in the Python
  `ibmmq` binding (since 2.0.2), the Node.js `ibmmq` binding (since 2.1.1), and Go
  `ibmmqotel` (since mq-golang 5.6.1) [S11][S16][S17]. These bindings only carry
  context. They do not create spans; the application must do that.
- **[judgment]** The real value for this lab is **distributed tracing of one message
  across queue-manager hops during a failover drill**, a per-hop view that today's
  metrics, logs and the DR Watcher ledger cannot give. OTel for metrics (`mq_otel`) and
  for logs adds almost nothing, because the lab already has both.
- **[judgment]** The full picture (client spans plus queue-manager and channel spans)
  depends on the optional exit. Getting that exit is unconfirmed (§4.3), and IBM lists
  support only up to MQ 10.0.0.0 while the lab runs 10.0.1.0. The Python binding's OTel
  code is young and carries traps that our failover-heavy clients would hit (§5).
  Against that cost and risk, **OTel may not be worth the effort for the lab yet.** The
  decision is left to a human to revisit; §9 lists what a future go-ahead would have to
  prove first.

## 2. What the lab has today

- **[data]** The lab already has **metrics**: Prometheus scrapes `node_exporter`,
  client-mode `mq_prometheus` (mq-metric-samples v6.0.0, keyed by queue manager so
  boards follow a failover) and `ha_cluster_exporter`; Grafana displays them
  (`docs/specs/2026-06-10-lab-observability-design.md` §3.3,
  `manifests/_shared/observability.yaml`).
- **[data]** It has **logs**: Alloy ships the journal, including MQ JSON diagnostic
  logs, to Loki, and optionally fans them out over **OTLP/gRPC** to Data Prepper's
  `otel_logs_source` and on to OpenSearch
  (`ansible/roles/alloy/templates/config.alloy.j2:99-123`,
  `ansible/roles/data-prepper/templates/pipelines.yaml.j2`). That fan-out is the lab's
  only OTel use today.
- **[data]** It has **message-level accounting**: the DR Watcher ledger
  (`components/mq-resiliency-clients/src/mqrc/dr/`) classifies loss by MsgId/CorrelId.
- **[data]** It has **no traces backend**, and **OTel is deliberately banned** from the
  clients' lock, because `ibmmq` changes behaviour automatically when OTel imports.
  That change was deferred when the lab moved to `ibmmq` (epic `.github#300`;
  `tests/test_clients_lock.py:1-6,31`).

## 4. The queue-manager tracing exit

### 4.1 OTLP without Instana

- **[data]** The exit "can generate span data in the OpenTelemetry format… sent to an
  OpenTelemetry protocol (OTLP) receiver, like OpenTelemetry Collector or Jaeger
  Collector" [S6].
- **[data]** Configuration lives in `/var/mqm/exits64/mqtracingexit.conf`, or
  `mqtracingexit_<QMNAME>.conf` for one queue manager. The documented keys are:
  - `SPAN_FORMAT="otel"` (default `"instana"`; it must match across MQ hosts);
  - `OTLP_EXPORTER_GRPC_ENDPOINT` (default `localhost:4317`) or `OTLP_EXPORTER_HTTP_URL`
    (example `http://localhost:4318/v1/traces`);
  - `OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_RESOURCE_ATTRIBUTES`.

  Every change needs a queue manager restart [S6].

### 4.2 Entitlement

- **[data]** The MQ 10.0 docs say: "Your IBM MQ entitlement only permits use of the IBM
  MQ Tracing exit component of the IBM Instana® supporting program. Separate
  entitlement is required for the component that collects trace data, such as IBM
  Instana or an OTel Collector. Issues arising from the use of the exit must be
  reported to IBM MQ Support unless you are using the tracing exit with an IBM Instana
  monitoring system and IBM Instana entitlement." [S1]
- **[judgment]** An OSS collector (Alloy, an OTel Collector, Tempo) carries its own OSS
  licence. No Instana licence appears to be needed for that path.

### 4.3 Getting it, platforms and versions (the viability concern)

- **[data]** Instana's install page downloads the exit from IBM's Artifactory with
  username `_` and "a valid agent key", which is an Instana credential. An
  unauthenticated request returned HTTP 401 [S6].
- **[data]** The MQ-side route `ibm.biz/mqinstanaexit` redirects to Fix Central
  (`fixids=*IBM-Instana-MQ-Tracing*`). The listing could not be confirmed because the
  page is rendered by JavaScript [S2].
- **[data]** Supported platforms are Linux x86_64, ppc64le and s390x, Windows x86_64,
  and AIX 7.2/7.3. **Linux aarch64 is not listed** [S7][S9]. The support table lists
  MQ up to **10.0.0.0** (latest technology version 10.0.0.5) [S7], and the lab runs
  10.0.1.0.
- **[data]** The exit needs OpenSSL 3.2.3 or later on Linux [S6].
- **[data]** Version information conflicts: the support page says 3.8.0 (rev 19.0,
  2026-06-17) [S9]; the install page links a 3.8.3 tarball [S6].
- **[judgment]** The aarch64 gap matters only on the Apple-Silicon host. Guest
  architecture follows the host (`lab/topology.yaml`, the per-arm comments), so on the
  x86 cloud host every arm is x86_64, and RDQM is x86-pinned everywhere.

### 4.4 Behaviour

- **[data]** `MONITOR_LEVEL` takes `off`, `quiet`, `normal` or `debug`, with per-queue
  regex overrides (`IBMMQ_DEST_MONITOR_LEVEL_*`) [S6].
  - At `normal`, trace context is added only to messages that already carry an RFH2
    header or properties.
  - At `debug`, it is added to every traced message, as RFH2 entries `X_INSTANA_T/S/L`,
    `traceparent` and `tracestate`. IBM warns this can break consumers and suggests
    `PROPCTL(NONE)` or the `QUIET` list [S8].
- **[data]** There is no sampling control, and no overhead figures are published.
  Logs go to `/tmp/ibmmqtrace` by default. If the libraries can't load, the queue
  manager fails to start [S6][S8].
- **[data]** No documented list says which MQI calls or channel agents produce spans.
  IBM's worked example shows producer and consumer spans, including the channel
  agent's transmission-queue get [S4] pp. 12–13.

## 5. The Python binding: the riskiest piece

The lab's clients use `ibmmq==2.1.1`. Its OTel code was read in the 2.1.1 and 2.1.2
sdists; the OTel and queue code is identical in both.

- **[data] Upstream issues.** At the time of writing, four of the seven open issues on
  `ibm-messaging/mq-mqi-python` are about OTel [S13]:
  - **#20**: a crash in the get path when a message handle is used. The fix is
    recorded in CHANGELOG 2.0.6 and is in the 2.1.1 code, but the issue is open.
  - **#28**: `trace_flags` is compared to 1 instead of tested as a bit, so a sampled
    span can lose its sampled flag. The maintainer said on 2026-09-01 it was fixed
    locally, and the 2.1.1 code tests the bit, but the issue is open.
  - **#26**: RFH2 unpack fails on EBCDIC messages from z/OS. Open and unfixed;
    **[judgment]** irrelevant to an all-Linux lab.
  - **#27**: a caller-supplied message handle gets no OTel properties. Open and
    unexplained.
- **[data] What turns it on.** Importing `opentelemetry.trace` successfully is enough;
  no span needs to be active (`ibmmq/__init__.py:194-198`, `mqotel.py:689-690`).
  Enabling it also sets `AMQ_OTEL_INSTRUMENTED=true` (`mqotel.py:684`).
- **[data] On put.** If the caller supplied no handle, it attaches **one shared handle
  per connection** to `pmo.OriginalMsgHandle` on every put, even with no active span.
  It sets `traceparent` only when a valid span is current (`mqotel.py:351-354,
  384-431`). The handle is cleared only after a *successful* MQPUT (`mqqueue.py:170-182`).
- **[data] On get.** It forces `MQGMO_PROPERTIES_IN_HANDLE` only for `NO_PROPERTIES`,
  or `AS_Q_DEF` on a `PROPCTL(NONE)` queue. To learn PROPCTL, it runs an MQINQ on every
  input open, using a hidden extra open if needed. It does not create spans; it only
  `add_link`s to a span that is already current (`mqotel.py:193-284, 453-668`).
- **[data] Error handling.** Errors when setting properties are swallowed
  (`except MQMIError: pass`, `mqotel.py:413-417, 427-431`). The RFH2 `unpack` on get is
  not guarded (`mqotel.py:581`), so a parse error reaches the caller after a
  destructive MQGET has completed.
- **[judgment] Impact.** Our clients reconnect after 2009 and reuse their `pmo`
  (`components/mq-resiliency-clients/src/mqrc/dr_flow.py:58`). After a failed put, the
  stale shared handle could carry an old `traceparent` or fail on the new connection.
  That is exactly the failover path the lab exists to exercise. **Unverified;** it
  needs a hands-on check (§9, S3).

## 6. A lab-side defect this R&D exposed

- **[data]** `svc_responder` copies the request's `Format` onto the reply and prepends
  `REPLY:` to whatever body it received
  (`components/mq-resiliency-clients/src/mqrc/svc_responder.py:90-101`). It gets
  without a message handle (`:85`).
- **[data]** No lab MQSC template sets PROPCTL, so queues default to `PROPCTL(COMPAT)`.
  A property with no prefix maps to the RFH2 `usr` folder. Under COMPAT, a getter with
  no handle receives those properties as an MQRFH2 header [S14][S15]. The #27 hex dump
  shows exactly that header [S13].
- **[judgment]** So once any request carries properties (from OTel, or any future
  JMS-style client), the responder replies with a body that starts `REPLY:` but is
  labelled MQHRF2. The requester gets the reply outside syncpoint
  (`app_requester.py:216-220`, no `MQGMO_SYNCPOINT`). With OTel on, the unguarded RFH2
  unpack would raise and the reply would be lost. With OTel off, the requester would
  read RFH2 bytes as the reply. This is latent today and **independent of an OTel
  decision**. It is recorded here and not filed, per the decision for this issue.

## 7. What OTel would add (value)

- **[judgment] Drill diagnosis (the payoff).** One trace per request/reply round trip:
  app-requester → app QM → transmission queue → channel → svc QM → responder → reply.
  During a failover it would show which hop stalled (client reconnect, transmission
  queue dwell, channel restart). That is a hop-level comparison of RDQM, Pacemaker and
  Native HA CRR, which the current per-QM metrics cannot give.
- **[judgment] Correlation.** Exemplars would link a latency spike on a Grafana board to
  the trace behind it, and the trace would link to its JSON log lines in Loki or
  OpenSearch.
- **[judgment] Demonstrating IBM's features.** It would exercise binding propagation,
  the tracing exit, and context flowing across channels, on all three HA arms.
- **[judgment] Little value:** `mq_otel` in place of `mq_prometheus` (identical
  metrics), and OTel for logs (already done).

- **[judgment]** A short-retention lab Tempo is probably far smaller than that guide,

- **[data]** Tempo would follow the Loki role pattern:
  - baked inert, and started in the metrics tier after the log tier
    (`ansible/site-obs.yml`, `tests/test_observe_startup_order.py`);
  - a pin in four places: role defaults, `manifests/_shared/observability.yaml`,
    `_OBS_VAR_MAP` in `src/mqlab/manifest.py`, and `tests/test_obs_version_sync.py`;
  - an obs rebake (`docs/development/box-model.md`).
