## 1. Goal

Stand up the project's published documentation site to the standard the
Vergil tooling repo sets, and make the **architecture** its centerpiece —
explained top to bottom as a layered, drill-down walkthrough carried by a
set of hand-authored HTML diagrams.

The site documents **what was built and how to run it**. It does not
replace the design spec (`docs/specs/…`), which remains the *why*. It is
also not the ops/observability tooling (#32), which it only
cross-references.

## 2. Scope

### Delivered this round

1. **Publishing proven end-to-end.** The existing `cd-docs` pipeline ships
   a real site to GitHub Pages on push to `develop`/`main`, with the
   Changelog and Release Notes pages live (auto-generated from
   conventional-commit history — not hand-authored).
2. **The site spine.** Home (overview), Getting Started, and the
   navigation skeleton modeled on Vergil tooling.
3. **The Architecture page.** The substantive deliverable: a layered,
   drill-down walkthrough of the lab, carrying the HTML diagram set.
4. **A light Design & Specs pointer.** An annotated index linking the
   existing `docs/specs/` and findings reports, so the engineering thread
   is visible from the site. Deep spec integration is deferred.

### Deferred to #33 follow-ons

Per-component reference pages, the operations/runbook section, and the
findings index. These are **not** stubbed as empty nav entries, because
`strict: true` turns an empty/missing page into a hard build failure. They
become nav tabs when their content lands.

### Out of scope

- The ops/observability tooling itself (#32) — cross-referenced only.
- Any change to the design spec's role.
- Auto-generating diagrams from `topology.yaml` (possible future; see
  risks).

## 3. Information architecture

The navigation keeps the Vergil tooling *spine*, trimmed to what this
round actually fills:

```
Home                  index.md               — what the lab is; orientation + start-here links
Releases
  Changelog           changelog.md           — generated by vrg-docs-stage
  Release Notes       releases/…             — generated; versions injected by vrg-docs-patch-nav
Getting Started       getting-started.md     — nothing → a running stack
Architecture          architecture/index.md  — the layered walkthrough + diagrams (centerpiece)
Design & Specs        design-and-specs.md    — annotated links into docs/specs/ (light integration)
```

The `Releases` block matches the template exactly so `vrg-docs-patch-nav`
operates unchanged. Components / Operations / Findings are added as tabs
when their content lands under #33.

## 4. Publishing mechanism

The pipeline already exists: `.github/workflows/cd.yml` calls
`vergil-project/vergil-actions/.github/workflows/cd-docs.yml@v2.1` on every
push to `develop`/`main`. On each run it:

1. **`vrg-docs-stage`** reads conventional-commit history and writes
   `changelog.md` + `releases/` pages into the docs tree **at build time**.
   These are never committed — they regenerate every run.
2. **`vrg-docs-patch-nav`** injects the discovered release versions into
   the `Releases → Release Notes` nav block.
3. **`mike`** deploys the built site to `gh-pages` as a versioned doc set
   and sets the default.

### What we change

Config, not toolchain. The template carries **no** `mkdocs`/`mike`
dependencies and no Makefile — the CI/CD container provides the toolchain.
So:

- Bring `docs/site/mkdocs.yml` up to the template's shape: add
  `site_description`, `repo_name`, `extra.version.provider: mike`, the
  `Releases` nav block, and the new content pages in `nav`.
- No `pyproject` dependency additions. No Makefile. The `make docs`
  phrasing in #33's acceptance resolves to "the cd-docs pipeline".

### Local verification

The implementation plan must pin down how to verify the docs build locally
before pushing: confirm whether `vrg-validate` already runs a docs
build-check, and if not, document the in-container `mkdocs build --strict`
invocation. `strict: true` makes any broken link or orphan nav entry a hard
failure — that is the safety net, and we want it to fire locally, not in
CI.

## 5. The diagram set

Five self-contained HTML files under
`docs/site/docs/architecture/diagrams/`, each iframe-embedded in the
Architecture page, each grounded in `lab/topology.yaml` (**as-built
only** — no aspirational topology):

| # | Diagram | Depicts |
|---|---------|---------|
| 1 | **Host & identity VMs** | The macOS host → the `vergil-user` VM, the `vergil-audit` VM, and the lab VM ("the big special one"). The Vergil identity model at the outermost layer. |
| 2 | **Inside the lab VM** | The nested-virtualization stack (M-series → macOS `vz` → Lima → KVM/TCG) and the network fabric — the libvirt networks (`net-data-a/b`, `net-hb-a/b`, `net-wan`, `net-dtcc`, `net-client`, `net-san-a/b`) with their isolation/severability roles — plus the node fleet on them. |
| 3 | **RDQM arm (Phase C)** | The canonical 3+3: `rdqm-a1..3` (synchronous HA in DC-A) + `rdqm-b1..3` (DC-B), asynchronous DR across `net-wan`. A refresh of the existing `topology-rdqm-ha-dr.html`, **with the active/active vision panel removed** (as-built only). |
| 4 | **Standalone QM arm (Phase B)** | `qm-main` + `dtcc-sim` + `app-client` on `net-client`/`net-dtcc` — the single-QM message path. |
| 5 | **Pacemaker/SAN arm (Phase D)** | `san-a` + `pcmk-a1..3` with the shared-SAN (`net-san-a`) HA model — the contrast to RDQM's replicated-storage approach. |

### Embedding

Each diagram is iframe-embedded so its self-contained dark styling stays
isolated from the Material theme (and still opens standalone in a browser).
Inline raw-HTML and Mermaid/SVG re-authoring were both rejected — see the
decisions log.

### Canonical home for the RDQM diagram

`docs/specs/diagrams/topology-rdqm-ha-dr.html` is currently spec-scoped.
The site tree becomes the canonical home: the refreshed, as-built version
lives under `architecture/diagrams/`. The plan decides whether to leave the
original in place as spec-historical or redirect it, so we do not maintain
two drifting copies.

### Aesthetic

All five diagrams share one small CSS vocabulary (the panel / node /
network-tag style already established in the existing diagram) so the set
reads as a coherent family as the reader drills down.

## 6. Content pages

- **Home (`index.md`)** — a tight orientation: what the lab *is* (a
  reproducible, nested-virtualization IBM MQ cluster lab for exercising HA
  and DR topologies), why it exists, and a start-here link set. One screen.
- **Getting Started (`getting-started.md`)** — the path from nothing to a
  running stack, as-built: build/enter the Vergil VM (`vrg-vm` from
  `vergil.toml`) → bring up the network fabric and a node set from
  `lab/topology.yaml` → stand up one stack end-to-end (the standalone QM
  message path is the simplest proof) and verify it. Orientation altitude,
  not the full per-arm runbook (deferred Operations section).
- **Architecture (`architecture/index.md`)** — the centerpiece. A
  top-to-bottom narrative that walks the same drill-down as the diagrams:
  host & identity VMs → inside the lab VM (nested virt + network fabric) →
  the node fleet → the three MQ-service arms. Each layer is a short prose
  explanation **plus** its iframe'd diagram, with design rationale woven in
  (e.g. *why* HA never stretches across the WAN; *why* the install DVD
  doubles as an offline repo). This is where #33's knowledge-transfer
  intent lives.
- **Design & Specs (`design-and-specs.md`)** — a short annotated index
  linking the existing `docs/specs/` (the lab design spec, the DR/HA
  validation framework spec) and the findings reports, framed as "how this
  was engineered." Links + one line of context each; no embedded spec
  content.

## 7. Verification & acceptance

- **Build is green under `strict: true`** — every nav entry resolves, no
  broken links or orphans. Verified locally via the in-container
  `mkdocs build --strict` (exact invocation pinned in the plan) before any
  push.
- **Pipeline publishes** — after merge to `develop`, `cd-docs` produces a
  live site with Changelog + Release Notes populated and all five diagrams
  rendering in their iframes.
- **Diagrams are accurate** — every node / network / IP shown traces back
  to `lab/topology.yaml`.
- **Per-section human sign-off** — consistent with #33's working mode: the
  human overseer gates each landed section as "understood and true."

## 8. Risks & watch-items

- **Diagram drift.** The diagrams are hand-authored snapshots of
  `topology.yaml`; if topology changes they go stale. Mitigation: they live
  beside the topology under version control and are part of the same review.
  Long-term auto-generation is a possible future, explicitly out of scope
  now.
- **Two copies of the RDQM diagram.** Resolved by picking one canonical
  home (§5).
- **Local docs-build parity.** If `vrg-validate` does not already cover
  docs, the plan documents the manual build-check so a green local build
  reliably predicts a green CI build.

## 9. Decisions log

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Scope of this round | Plumbing + Architecture page; defer component/ops/findings | Sequenced delivery; prove publishing + land the highest-value content first. |
| As-built vs roadmap | As-built only | #33 documents what was built; roadmap content would blur reality. |
| Diagram set shape | Layered drill-down + a diagram per arm | Coherent top-to-bottom story; each MQ arm gets first-class treatment. |
| Diagram embedding | iframe self-contained HTML | Style isolation from Material; diagrams open standalone; easy to evolve. Inline HTML fights the theme; Mermaid can't express the nested-box aesthetic. |
| Information architecture | Vergil spine, trimmed to filled pages | Familiar shape; `strict: true` forbids empty nav entries. |
| Toolchain changes | None (config only) | Template carries no mkdocs/mike deps; CI container provides them. |
