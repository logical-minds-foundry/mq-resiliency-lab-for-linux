# Ansible → Salt migration evaluation — design

- **Issue:** #197
- **Date:** 2026-06-16
- **Status:** design (methodology spec)
- **Type:** evaluation / decision-support (no production change)

## 1. Purpose

The lab's configuration automation is Ansible today. A new employer runs Salt,
not Ansible, for Unix configuration management. This evaluation decides whether
the lab should migrate, and if so, how large the effort is.

The deliverable is a written **evaluation report** that:

1. Gives a **go/no-go recommendation**, weighing benefit (employer-fidelity,
   deliberate skills practice) against cost and risk.
2. If go, **sizes the effort** as a phased t-shirt estimate with named risk
   hotspots.

This document is the **methodology spec**. Executing its plan *conducts* the
evaluation and produces the report. No automation is migrated here.

## 2. Background — current Ansible footprint

Grounding the estimate (surveyed 2026-06-16):

- **8 playbooks, 21 roles, 21 Jinja2 templates, ~2,260 lines.**
- **Zero Galaxy collections** — pure `ansible-core` builtins. No
  `community.general`, no `ibm.ibm_mq`. All MQ logic is `shell`/`command`
  against `/opt/mqm/bin`.
- **Shell-heavy:** 36 `shell` + 21 `command` tasks orchestrating `pcs`,
  `drbdadm`, `iscsiadm`, `rdqmadm`, `runmqsc`.
- **Idempotency** is a mix of native modules (`apt`/`dnf`/`systemd`/`template`/
  `copy`/`lineinfile`) and hand-rolled `changed_when` / `creates` /
  `run_once`+`register` cluster coordination.
- **No vault, no dynamic inventory, no custom modules/plugins.** Secrets via
  env vars; static `inventory.ini` generated by `src/mqlab/inventory.py`.
- Invoked by the `mqlab` Typer CLI shelling out to `ansible-playbook`.

A small, self-contained, idiom-heavy footprint — which is what makes a
lightweight evaluation appropriate.

## 3. Core framing — two decoupled axes

The evaluation separates two decisions that are easy to conflate:

| Axis | What it is | Cost | Footprint impact |
|---|---|---|---|
| **1. Content authoring** | Port playbooks/roles → SLS formulas | ≈ all the effort | **None** — SLS is identical either transport |
| **2. Transport** | salt-ssh vs master+minion | Small, swappable | salt-ssh: zero. Master/minion: +1 master VM, +agent per node |

**Why this holds:** Salt's state content (SLS files / formulas) is
transport-independent. `salt-ssh` uses the same `file_roots` and `pillar_roots`
as a master and runs an unmodified state tree — the master compiles the run and
ships the rendered states plus referenced `salt://` files down in a tarball over
SSH. The authoring work in Axis 1 is therefore the same regardless of transport.

References:

- Salt SSH — https://docs.saltproject.io/en/latest/topics/ssh/index.html
- Standalone Minion — https://docs.saltproject.io/en/3007/topics/tutorials/standalone_minion.html
- Salt FAQ — https://docs.saltproject.io/en/latest/faq.html

**What salt-ssh gives up** (honest caveats): it is slower (re-ships the salt
thin + state tarball each run), and the event-driven half of Salt — mine,
reactor, beacons, `publish.publish`/peer — does not work the same way. **The lab
uses none of that machinery**; its automation is pure push-apply provisioning,
the direct analog of `ansible-playbook`. So salt-ssh covers the use case while
preserving the agentless, no-master, ephemeral footprint.

**Baseline decision:** the evaluation targets **salt-ssh**. Master/minion is
documented as an **optional later overlay** (what it adds: employer-fidelity, the
event-driven features; what it costs: +master VM, +agent/node) and is explicitly
*not* a prerequisite for Axis 1. Adding it later does not invalidate any
Axis-1 work — and the SLS/formula content one writes and showcases is identical
to what a master/minion shop writes, so employer-fidelity is *mostly* satisfied
by Axis 1 alone.

## 4. Method

Approach: **translation matrix + one thin vertical spike + scored
recommendation.** The matrix makes the estimate defensible and surfaces unknowns
explicitly; the spike turns "I think it translates" into measured evidence,
retiring the two stated risks (knowledge stale since 2022; unknown current Salt
ecosystem).

### 4.1 Translation matrix

Every idiom in the footprint mapped to its Salt equivalent, with a **confidence**
rating and an **effort weight**. Draft target mappings (to be confirmed/corrected
during the evaluation):

| Ansible idiom | Salt equivalent | Notes / risk |
|---|---|---|
| `apt` / `dnf` (cross-distro) | `pkg.installed` + grain-based targeting | grains replace `ansible_os_family` |
| `systemd` | `service.running` (+ `enable`) | native |
| `template` (.j2) | `file.managed` + `template: jinja` | Jinja engine differs — filter set is not identical |
| `copy` | `file.managed` (inline `contents`) | native |
| `file` | `file.directory` / `file.symlink` | native |
| `lineinfile` / `blockinfile` | `file.line` / `file.blockreplace` | native |
| `unarchive` + `creates` | `archive.extracted` | native idempotency |
| `shell` / `command` + `changed_when` | `cmd.run` + `onlyif` / `unless` | **high-volume idiom** (36 + 21 uses) |
| handlers / `notify` | `mod_watch` + `watch` / `listen` requisites | semantics differ |
| `include_role` / `import_playbook` | `include` / orchestrate | native |
| `run_once` + `register` cluster coordination | orchestrate runner / mine, or keep imperative | **highest-risk cell** |
| static `inventory.ini` (from `inventory.py`) | salt-ssh **roster** (from `topology.yaml`) | regenerate target, not reuse |
| `group_vars/all.yml` | pillar | native |
| `ansible.cfg` | `Saltfile` / config | native |
| `mqlab` → `ansible-playbook` subprocess | `mqlab` → `salt-ssh` subprocess | CLI invocation swap |

### 4.2 Thin vertical spike

Port a single representative role to an SLS formula and run it **agentless via
`salt-ssh`** (a roster pointing at one live lab node).

- **Target role:** `prometheus` — self-contained, needs no MQ-entitlement
  artifacts, and exercises the common idiom cluster in ~90 lines: `user`,
  `file`, `get_url` + `unarchive` (with `creates`), `template`, `systemd`, and a
  **handler**. (Alternative if the codebase's signature shell-idempotency idiom
  is preferred for calibration: `mq-install` — but it requires MQ tars present.)
- **Success criterion:** **idempotent apply** — run twice; the second run is a
  clean no-op.
- **Record:** actual effort (time/LOC) and every surprise, to calibrate the
  matrix weights and per-role-class estimate.
- **Throwaway:** a scratch formula on this feature branch, never merged into the
  lab automation.

### 4.3 Scored recommendation + phased estimate

Roll the matrix weights — calibrated by the spike's measured effort — into a
t-shirt size per role-class and an overall go/no-go. The recommendation weighs
benefit (employer-fidelity, skills) against cost (authoring effort) and risk
(the hotspots below).

## 5. Risk register

Explicitly tested or flagged in the report:

- **`run_once` + `register` cluster coordination** (pcs / DRBD / iSCSI) — the
  cell least likely to map cleanly. The report names the chosen Salt pattern
  (orchestrate runner, mine, or retained imperative `cmd.run`) and its
  confidence.
- **Jinja filter parity** — Ansible's `map(attribute=…)`, `default`, `from_json`
  vs Salt's filter set; flag any template needing rework.
- **`changed_when` → `onlyif` / `unless` fidelity** across the 57 shell/command
  tasks.
- **Roster generation** — `inventory.py` currently emits `inventory.ini`; Salt
  needs a roster. New small target, not a reuse.
- **`mqlab` integration + cold-rebuild** — the CLI swap, and whether salt-ssh
  fits the one-pass cold-rebuild acceptance gate.

## 6. Scope boundaries (YAGNI)

- **In:** the translation matrix, one salt-ssh spike, the written report.
- **Out:** any real migration; the master/minion overlay build; event-driven
  (reactor / beacon / mine) work; touching live lab state.
- The spike is **throwaway**.
