# RDQM vs. pacemaker-drbd — deviation ledger

This ledger is the source of truth for what IBM RDQM adds on top of the open-source
parts. It has one row per RDQM element, and every row cites the blueprint file it comes
from, under `docs/reference/rdqm-blueprint/`. See the
[blueprint README](rdqm-blueprint/README.md) for the full reading.

Status values:

- **exact**: the same upstream component with the same configuration.
- **partial**: the same behaviour through a different mechanism or different values.
- **none**: no open-source equivalent is built.
- **pending**: the open-source side is not built yet. Task 9 of epic
  logical-minds-foundry/.github#310 replaces every `pending`.

How a difference is judged (owner ruling, 2026-10-18, #1621): RDQM's behaviour is the
minimum the open-source arm must meet, not a limit on it. The aim is to stay compatible
with RDQM. Where the open-source arm does better than RDQM, for example by being more
secure, the difference is welcome: the row stays `partial`, says it is stricter or better,
and counts in the open-source arm's favour in the Task 9 comparison. Falling short of
RDQM is a gap to close or to record as a deliberate deviation.

Row IDs are stable: `ST` storage, `RP` replication, `CL` cluster, `DR` disaster
recovery, `TL` lifecycle tooling, `SC` replication security, `SP` support and
installation. Blueprint paths below are relative to `docs/reference/rdqm-blueprint/`.

Seeded by #1425 from the 2026-10-16 capture. The pacemaker-drbd column states the
**plan's** intended equivalent. Where the blueprint contradicts that plan on a
structural point, the row says so, and the affected task (#1427 or #1428) is revised
before it starts.

#1427 (site-A HA, HA-only shape) set the rows it builds to their as-built status, read
from the configuration its code renders: ST-2, ST-3, RP-2, RP-4, RP-6, RP-7, CL-2, CL-3,
CL-4, CL-6 to CL-10 and TL-5. Its live bring-up confirms them. Rows whose as-built value
can only be read from a running node (for example the corosync settings in CL-1 and SC-2,
the units in TL-4, the versions in RP-8 and SP-1) stay `pending`, as do the rows that
need site B or the DR resource (Task 6, #1428).

#1428 (site B, the stacked DR resource, the DR switch) set the rows it builds the same
way, from the configuration its code renders: ST-4, RP-1, RP-5, the DR half of RP-7,
CL-5, CL-10, DR-1, DR-2 and TL-2. Its live bring-up and switch drill (plan Task 6
Step 7) confirm them. RP-3 stays `pending`: it is settled by the WAN-cut drill (Task 8

(2026-10-18: every HA and DR connection on all six nodes Connected with `tls:yes`, kTLS
counters two sockets per connection, still so after a cutover and a failback), and RP-5 to
`exact` by naming the DR resource's logical peer `encrypted.remote`, as RDQM does. SC-1 is
`partial` for the differences its row lists, not for want of proof; the 24.04 path is not
yet run live.
