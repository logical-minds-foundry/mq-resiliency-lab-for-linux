## 1. Top findings

1. **Native HA monitoring change: no break, one small opportunity.**
   *What's changed* lists "Change in Native HA monitoring on Linux platforms".
   The change is **additive**: IBM's `mqmonitor.py` sample and
   `mqmonitor@.service` template gained a `--reload` action and an
   `ExecReload=` line, so `systemctl reload mqmonitor@<QM>` now does the
   equivalent of `endmqm -r` (end and restart the QM, telling reconnectable
   clients to reconnect). The health check, the accepted `dspmq` states, the
   `strmqm -x` return codes, the stop command and `SyslogIdentifier=mqmonitor`
   are unchanged from the 9.4 sample. The lab's HA/DR collectors
   (`mqro.nativehastate`, `mqro.loglifecycle`) parse `dspmq -o nativeha -x/-g`,
   not the monitor, and were proven live on 10.0.1 by
   [#1474](https://github.com/logical-minds-foundry/mq-resiliency-lab-for-linux/issues/1474).
   No fix task is needed. See §3.1.
2. **LTPA keystore password change: no impact on the lab today.** The
   `ltpaKeysPassword` property is removed and `strmqweb` now runs
   `setmqweb security -i` on every start. The lab never set `ltpaKeysPassword`,
   serves mqweb TLS from its own `keyStore` element (not the default keystore),
   and runs per-node mqweb **off by default** (`mqweb_enabled: false`, #1171).
   See §3.2.
3. **PQ key exchange on MQ channels is not new in 10.0.1, and the lab is not
   using it yet.** IBM says ML-KEM and Hybrid ML-KEM key exchange arrived for the
   C client and queue managers "From IBM MQ 10.0" (`SSLQS`/`SSLQSR` on channels,
   `QuantumSafeAlgorithm` in the MQCD and CCDT). Every lab channel already uses
   `ANY_TLS13_OR_HIGHER`, but none sets `SSLQS`, and the outbound side must ask
   for PQ. So today every lab channel uses a classical key exchange. This is the
   biggest and cheapest security gain available. See §4.
4. **Native HA PQ is the new 10.0.1 headline, and it covers CRR.** IBM's 10.0.1
   *What's new* says Native HA, Native HA CRR **and** Native HA IRR can use
   quantum-safe connections. It is set in `NativeHALocalInstance`
   (`QuantumSafeAlgorithm`, `QuantumSafeRequired`) and **needs TLS 1.3**. The lab's
   Native HA stanzas use `CipherSpec=ANY_TLS12` on both stacks, so adoption needs
   a cipher move as well as the two new settings. See §4.2.
5. **Developer edition covers every adopted feature.** IBM says MQ Advanced for
   Developers "provides the full set of capability available with IBM MQ
   Advanced". One exception affects the lab: MQTT is not available on the ARM64
   Developer build, so an MQTT demo would run only on the x86-64 host. See §6.

## 3. Priority triage

### 3.1 Native HA monitoring on Linux

**What changed.**

- **[data]** 10.0.1 *What's changed*: "The script and template service
  definition, mqmonitor.py and mqmonitor@.service … have been updated. The
  systemctl reload command can now be used to provide the equivalent action to
  endmqm -r."
  (<https://www.ibm.com/docs/en/SSYHRD_10.0.0/overview/mq1001_changed.html>)
- **[data]** The 10.0.x sample adds `qmstop(..., client_reconn=False)` (appends
  `-r` to `endmqm`), a `qmreload()` that stops with reconnect and then starts, a
  `--reload` argument, and
  `ExecReload=/usr/bin/python3 ${MQ_INSTALLATION_PATH}/samp/mqmonitor.py … --reload %I`
  in the unit. IBM: "`sudo systemctl reload mqmonitor@MYQMGR` … (This is the
  equivalent of using the endmqm -r command)."
  (<https://www.ibm.com/docs/en/SSYHRD_10.0.0/configure/monitoring_nativeHA.html>)
- **[data]** Compared with the 9.4 sample
  (<https://www.ibm.com/docs/en/SSFKSJ_9.4.0/configure/monitoring_nativeHA.html>),
  the following are **unchanged**: `qmhealthy()` runs `dspmq -n -m <QM>` and
  accepts the same six states (`RUNNING`, `STARTING`, `RUNNING AS STANDBY`,
  `NEGOTIATING`, `REPLICA`, `RECOVERY GROUP LEADER`); `qmstart()` accepts
  `strmqm -x` return codes 0, 30 and 94; the stop is `endmqm -tp 29 -w`; the
  10-second health interval; and the unit's `User=mqm`, `Type=simple`,
  `SyslogIdentifier=mqmonitor`, `TimeoutStopSec=30`, `KillMode=mixed`,
  `Restart=always`. (Only the copyright header and the new reload path differ.)

**How the lab uses it.**

- **[data]** (repo) `ansible/roles/mq-nativeha/tasks/main.yml` **symlinks**
  `/opt/mqm/samp/mqmonitor@.service` into `/etc/systemd/system/` and adds only a
  drop-in for the open-files limit. The lab never copies or edits the sample, so
  a 10.0.1 install picks up IBM's new unit and script automatically.
- **[data]** (repo) The `qm-up`/`qm-down` verbs in `lab/topology.yaml` are
  `systemctl start|stop mqmonitor@{qm}`. Neither changed.
- **[data]** (repo) The HA/DR collectors
  (`components/mq-resiliency-observability/src/mqro/nativehastate.py`,
  `loglifecycle.py`) shell out to `dspmq -m <qm> -o nativeha -x` and `-g`. They
  do not read anything from the monitor. The Alloy journal relabel in
  `ansible/roles/alloy/templates/config.alloy.j2` keys on the
  `mqmonitor@<QM>.service` unit name, which is unchanged.
- **[data]** [#1474](https://github.com/logical-minds-foundry/mq-resiliency-lab-for-linux/issues/1474)
  (Outcome: SUCCESS) cold-rebuilt the Native HA rows on MQ 10.0.1 and checked
  that "the MQ exporter and HA/DR collector series are live and carry data".

**Verdict [judgment].** Nothing the lab relies on is broken or changed. The
`dspmq -o nativeha` output format is not mentioned in the change list, and the
live 10.0.1 validation shows the collectors still parse it. The only new thing
is an **opportunity**: a `qm-reload` verb (`systemctl reload mqmonitor@{qm}`)
gives Native HA stacks a first-class "restart with client reconnect" drill,
equivalent to `endmqm -r` on the other arms. It pairs naturally with
`mqrc.reconnect_probe`. Listed as follow-on F5.

### 3.2 LTPA keystore password for MQ Console and REST API

- **[data]** "The ltpaKeysPassword configuration property is removed … This
  password is now generated automatically, by the new setmqweb security
  command … When you run the strmqweb command, the setmqweb security command is
  called automatically … The -i parameter is specified by default."
  (<https://www.ibm.com/docs/en/SSYHRD_10.0.0/overview/mq1001_changed.html>)
- **[data]** `server.env` now holds a separate `ltpa_keys_password` ("new in IBM
  MQ 10.0.1") and `keystore_password` (the default HTTPS keystore). Before
  10.0.1 the keystore password also encrypted `ltpa.keys`, so "changing one
  password invalidated LTPA tokens and also the TLS keystore password". If mqweb
  is running, `setmqweb security` "exits immediately without making any
  changes" (MQWB1164W). `MQWEB_SKIP_DEFAULT_SECURITY_INIT` skips the `-i` step
  for setups that manage `server.env` externally or share `ltpa.keys` across
  nodes.
  (<https://www.ibm.com/docs/en/SSYHRD_10.0.0/refadmin/setmqweb_security.html>)
- **[data]** (repo) A search for `ltpa` across `ansible/`, `lab/`, `src/` and
  `components/` finds nothing: the lab never sets `ltpaKeysPassword`. The
  `mqweb` role runs only `setmqweb properties -k httpHost` (still supported),
  starts mqweb with `strmqweb` from a systemd unit, and serves TLS from its own
  `<keyStore id="mqwebKeyStore" …>` element in `mqwebuser.xml` (the lab-PKI
  `mqweb` entity, `sslProtocol="TLSv1.3"`), not from the default keystore.
- **[data]** (repo) Per-node mqweb is gated off (`mqweb_enabled: false`,
  `ansible/group_vars/all/admin.yml`, #1171/#1188). Its return is undecided
  (.github#266).
- **[data]** (repo, later update) The gate was removed in #1502 (epic `.github#341`):
  mqweb now runs on every QM node by default.
- **[data]** (repo, later update) #1598 removed the `setmqweb properties -k httpHost`
  call. The `mqwebuser.xml` template already sets
  `<variable name="httpHost" value="*"/>`, and it is now the file's only writer.

**Verdict [judgment].** No impact. When mqweb is enabled, the automatic `-i` step
just generates `server.env` passwords the lab does not otherwise use. Two notes
for whoever revives mqweb (.github#266): (1) the extra init step is one more
thing in Liberty's slow cold start, which #1154 measured as infeasible per node;
(2) on Native HA each node's mqweb has its own `ltpa.keys`, so Console sessions
do not survive a move to another instance. That is a known limit of per-node
mqweb, not a 10.0.1 regression. The lab's basic-auth REST calls are unaffected.

### 3.3 Quantum safe connections for Native HA

- **[data]** Scope: "Native HA, Native HA CRR, or Native HA IRR configurations."
  For CRR "the link that carries the log replication data between the two groups
  at separate sites must be protected" by TLS; within-group TLS is optional.
  "Where TLS protection is implemented, you can also specify that quantum safe
  protection is required … Quantum safe connections are only supported with TLS
  1.3 CipherSpecs."
  (<https://www.ibm.com/docs/en/SSYHRD_10.0.0/configure/QSforNAtiveHA.html>)
- **[data]** Configuration is two optional `NativeHALocalInstance` keys:
  - `QuantumSafeRequired=No|Yes` (default `No`). "When set to No, the TLS
    handshake can optionally use a post-quantum key exchange … When set to Yes,
    the TLS handshake must use a post-quantum key exchange."
  - `QuantumSafeAlgorithm=None|MLKEM|HYBMLKEM` (default `None`). `MLKEM` adds
    `mlkem768`, `mlkem1024`. `HYBMLKEM` adds `x25519mlkem768`,
    `secp256r1mlkem768`, `secp384r1mlkem1024`. Both keep the five classical
    groups.
  (<https://www.ibm.com/docs/en/SSYHRD_10.0.0/configure/NativeHALocalInstance_stanza.html>)
- **[data]** IBM's CRR example uses `CipherSpec=ANY_TLS12` (within group) with
  `GroupCipherSpec=ANY_TLS13` (cross-site), so PQ is negotiated "between the two
  groups, but not between the nodes within each group". The IRR example sets
  `GroupCipherSpec=ANY_TLS13`, `QuantumSafeRequired=Yes`,
  `QuantumSafeAlgorithm=MLKEM`.
  (<https://www.ibm.com/docs/en/SSYHRD_10.0.0/configure/QSforNAtiveHA.html>)
- **[data]** The hardening guide adds, for Native HA: keystore "created with the
  -pqc true flag"; `CipherSpec` and `GroupCipherSpec` set to TLS 1.3;
  certificates RSA ≥ 2048 or ECDSA ≥ 256 with SHA-256 or better;
  `QuantumSafeAlgorithm` not `NONE`; `QuantumSafeRequired=Yes` to enforce.
  (<https://www.ibm.com/docs/en/SSYHRD_10.0.0/secure/quantumsafe_hardening.html>)
- **[data]** FIPS: "Quantum Safe algorithms are not currently supported if FIPS
  is enabled."
  (<https://www.ibm.com/docs/en/SSYHRD_10.0.0/secure/quantumsafe_tls.html>)
- **[data]** Developer edition: see §6. It is an Advanced-entitlement feature,
  and Developer edition has "the full set of capability available with IBM MQ
  Advanced".

**Lab gap [data, repo].** `ansible/roles/mq-nativeha/tasks/tls.yml` and
`crr.yml` render `CipherSpec=ANY_TLS12` with no `GroupCipherSpec`, so one TLS
1.2 setting covers both the within-group and cross-site links (per
`tls-coverage.md` rows 5–6, negotiated `ECDHE_RSA_AES_256_GCM_SHA384`). The
choice of TLS 1.2 is not justified anywhere in the repo. It follows IBM's 9.4
examples.

**Target [judgment].** Both Native HA stacks, every instance, both groups:

```ini
NativeHALocalInstance:
   CipherSpec=ANY_TLS13
   GroupCipherSpec=ANY_TLS13          ; CRR stacks only; explicit, not inherited
   CertificateLabel=<entity>
   KeyRepository=/var/mqm/qmgrs/<QM>/ssl/key
   QuantumSafeAlgorithm=HYBMLKEM
   QuantumSafeRequired=Yes
```

`HYBMLKEM` (hybrid) rather than pure `MLKEM`: the hybrid groups keep a classical
X25519/ECDH share alongside ML-KEM, so the link is no weaker than today even if
ML-KEM were ever found flawed. IBM itself describes hybrid as combining PQ with
"the traditional system to provide confidence". Pure `MLKEM` is a possible
second demo setting, not the default. `QuantumSafeRequired=Yes` turns "PQ when
possible" into an assertion: if the handshake can't negotiate PQ, the link
fails loudly instead of quietly falling back. That matches the lab's
no-silent-downgrade rule.

**Open questions (to-verify, in the spike).**

- The lab's keystores are PKCS#12 files made by OpenSSL (`community.crypto`,
  RSA 4096, `compatibility2022` encoding), not by `runmqakm -keydb -create`. The
  docs do not say what `-pqc true` changes inside a keystore, or whether an
  OpenSSL-made file counts. The spike must test it first. If PQ will not
  negotiate, the fix is to re-wrap the same keys with `runmqakm … -pqc true`.
- Whether `ANY_TLS13_OR_HIGHER` (the channel alias the lab uses) is accepted in
  `NativeHALocalInstance`. IBM's examples use only `ANY_TLS13`.
- How to confirm the negotiated group on a Native HA link: probably the new
  AMQ3333–AMQ3336 messages. Their text was not fetched.
- Whether the ARM64 Developer build includes GSKit's ML-KEM. The key-share
  table is labelled "AIX, Linux, and Windows" with no architecture caveat
  (<https://www.ibm.com/docs/en/SSYHRD_10.0.0/secure/tls_keyshares.html>).
  Test on the macOS arm64 host.

## 4. TLS and post-quantum: the state of MQ 10.0.1

### 4.1 Where MQ supports PQ key exchange

| Surface | PQ key exchange? | Since | Configured by [data] |
|---|---|---|---|
| QM↔QM channels (SDR/RCVR, cluster) | Yes: ML-KEM, Hybrid ML-KEM | 10.0 | `SSLQS` on the **outbound** end; `SSLQSR(REQUIRED)` to enforce; inbound accepts by default |
| C client → QM (CLNTCONN/SVRCONN) | Yes | 10.0 | MQCD `QuantumSafeAlgorithm` / `QuantumSafeRequired`, or the CCDT (`transmissionSecurity.quantumSafeAlgorithm` / `quantumSafeRequired` in JSON) |
| Native HA, CRR, IRR replication | Yes | **10.0.1** | `NativeHALocalInstance` `QuantumSafeAlgorithm` / `QuantumSafeRequired` (§3.3) |
| Java / JMS / .NET clients | Runtime-dependent | n/a | "use the default configuration of the underlying technology" |
| Advanced Message Security (AMS) | **No** | n/a | "there is no support for the quantum safe algorithms available within Advanced Message Security" |
| MQ web server (Console/REST, Liberty) | **No data** | n/a | Not mentioned in the Quantum Safe topics; it depends on Liberty and Semeru 25 |
| MQTT (MQXR, Java) | **No data** | n/a | MQTT channels gain MQ CipherSpec names and TLS 1.3, but no `SSLQS` is documented |
| RDQM replication (kernel TLS, `tlshd`) | **No data** | n/a | Outside MQ's TLS stack; it depends on `tlshd`/GnuTLS |

Sources:

- **[data]** "From IBM MQ 10.0, support for FIPS 203 ML-KEM algorithms has been
  added to AIX, Linux, and Windows C client and queue managers … On outbound
  channels (or client applications) this is achieved by explicitly setting the
  use of a quantum safe algorithm. On inbound channels, quantum safe algorithms
  are always supported unless disabled through the AllowedQuantumSafeAlgorithms
  queue manager configuration option." With `SSLQSR(REQUIRED)`, a channel that
  does not use PQ "will immediately terminate with an AMQ9681 error message".
  The negotiated algorithm shows as `SSLQS` in `DISPLAY CHSTATUS`.

### 4.3 Per-hop current vs best achievable

Row numbers match [`tls-coverage.md`](tls-coverage.md) §2. "Current" is
**[data, repo]**. "Best achievable" is **[judgment]**, built from the §4.1 data.
Every row is mutually authenticated with the lab PKI roles (`app-org` /
`svc-org` CAs, per-QM entity certs, `SSLPEER` pins). PQ changes only the key
exchange. Certificates stay RSA, because MQ 10.0.1 documents no ML-DSA
certificate support (no data).

| # | Hop | Current | Best achievable on 10.0.1 | Change needed |
|---|---|---|---|---|
| 1 | App client → app QM (`APP.SVRCONN`) | TLS 1.3 (`ANY_TLS13_OR_HIGHER`), mutual, classical key exchange (clients set no `QuantumSafeAlgorithm`) | TLS 1.3 + **Hybrid ML-KEM required** | `mqrc` clients set `cd.QuantumSafeAlgorithm = MQQS_HYBMLKEM` (ibmmq ≥ 2.1.0; add to `ibmmq_refs`); then `SSLQSR(REQUIRED)` on `APP.SVRCONN` |
| 2 | Exporter → app & svc QMs (`MON.SVRCONN`) | TLS 1.3, mutual, classical (JSON CCDT has only `cipherSpecification` + `certificateLabel`) | TLS 1.3 + Hybrid ML-KEM required | Add `quantumSafeAlgorithm` (and `quantumSafeRequired`) to `exporter-ccdt.json.j2`; the exporter is built on the 10.0.1 C client, which reads the CCDT (**to-verify** live); then `SSLQSR(REQUIRED)` on `MON.SVRCONN` |
| 3 | Inter-QM, app side (`<QM>.SVCQM` SDR / `SVCQM.<QM>` RCVR) | TLS 1.3, mutual, classical | TLS 1.3 + Hybrid ML-KEM required | `SSLQS(HYBMLKEM) SSLQSR(REQUIRED)` on the SDR; `SSLQSR(REQUIRED)` on the RCVR (`mq-inter-qm` role) |
| 4 | Inter-QM, svc side + `SVC.SVRCONN` (svc counterparty) | TLS 1.3, mutual, classical | TLS 1.3 + Hybrid ML-KEM required | Same on `SVCQM.<QM>` SDR / `<QM>.SVCQM` RCVR (`their-side.mqsc.j2`); svc responder sets the MQCD field; `SSLQSR(REQUIRED)` on `SVC.SVRCONN` |
| 5 | Native HA within-group replication | **TLS 1.2** (`ANY_TLS12` → `ECDHE_RSA_AES_256_GCM_SHA384`), classical | TLS 1.3 + Hybrid ML-KEM required | `CipherSpec=ANY_TLS13`, `QuantumSafeAlgorithm=HYBMLKEM`, `QuantumSafeRequired=Yes` (§3.3) |
| 6 | Native HA **CRR** cross-region replication | **TLS 1.2** (same single `CipherSpec`), classical | TLS 1.3 + Hybrid ML-KEM required | Add `GroupCipherSpec=ANY_TLS13` + the two QS keys (§3.3) |
| 7–8 | RDQM HA / DR replication | Kernel TLS via `tlshd` (`crtmqm -re`), certs SAN `encrypted.remote` | **No data** from MQ; any PQ comes from `tlshd`/GnuTLS on RHEL 10, which MQ does not configure | Research only (follow-on F7); no MQ setting exists |
| — | MQ web / REST / Console (Liberty, 9443) | HTTPS, `sslProtocol="TLSv1.3"`, lab-PKI `mqweb` cert; **off by default** | TLS 1.3; PQ **no data** (Liberty / Semeru 25 JSSE) | None now; revisit with .github#266 |
| — | HA/DR collectors (`dspmq`, `rdqmstatus`, `crm_mon`) | Local CLI on each node; no network hop | n/a | None |

**[judgment] Rollout order.** Inbound already accepts PQ (default `ALL`), so
turning on `SSLQS` at each initiator is safe on its own: it falls back to
classical if PQ fails. Run in two passes. First, every initiator asks for
`HYBMLKEM`, and `DISPLAY CHSTATUS(*) SSLQS` proves every running channel shows
a non-`NONE` value. Second, flip `SSLQSR(REQUIRED)` everywhere. Flipping
`REQUIRED` first would break any initiator not yet converted, at runtime, with
AMQ9681.

**[judgment] Keep `ANY_TLS13_OR_HIGHER`, not a pinned CipherSpec.** The alias
already selects TLS 1.3. Pinning one suite (for example `TLS_AES_256_GCM_SHA384`)
gains AES-256 only, which IBM's PQ guidance calls a preparation step ("uses a
AES-256 encryption algorithm"), at the cost of agility. That trade is worth a
separate decision, not a default.
